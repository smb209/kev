Kev on DGX Spark

Can our two DGX Sparks serve Kev-27B, run it quantized, fine-tune the small Kevs on our own data, and how does Kev compare with Cloudflare's Clef? Every result below was pre-registered before its data existed, scored against reference runs, and reviewed by an adversarial second pass. Corrections are kept, not hidden.

Question 1

Serving Kev-27B on one Spark

Kev-27B v2 (51 GB of bf16 weights, hash-verified against the release) loads and serves on a single Spark with no changes to Kev's code. Two environment fixes were needed: PyTorch's aarch64 wheel on PyPI is CPU-only, so the venv installs the CUDA 12.9 build; and ~/.triton is root-owned on both boxes, so TRITON_CACHE_DIR must point inside the project.

Speed is set by memory bandwidth. Each forward pass reads all 51 GB of weights at about 224 GB/s, a floor of 0.23 s per pass, and CUDA graphs don't help because the Spark isn't launch-bound. Measured: 588 ms for a 2-question request with a new state, 304 ms with a cached state (H200: 40 / 22 ms), and 3.8 requests/s at 64 concurrent clients (H200: 39.7). Cold start is 5–7 minutes.

Question 2

NVFP4 Kev-27B

There is no official quantized Kev. The only community NVFP4 build of v2 ships as a 19 GB pickle that its own README says loads with weights_only=False, so we did not load it. Instead we built spark/kev_quant.py: it replaces the backbone's Linear layers with FP8 or NVFP4 versions at load time, using FlashInfer's FP4 CUTLASS kernels (about 250 TFLOPS on the GB10, against 78 for bf16) and static activation scales calibrated on a split that is never scored.

Question 4

Clef and Clef-Flash against Kev

Cloudflare's Clef (27B, on the same Qwen3.8-27B base as Kev-27B) and Clef-Flash (9B) speak the same System One API, also accept images and video, and score all questions in one joint pass. We hand-reviewed their loader code, pinned the revision and file hash, and scored them through Kev's own harness. A control confirmed that this HTTP path reproduces Kev-9B's local answers exactly (0 of 3,075 differ).

Question 5

Clef-Flash on a 16 GB Ada card

Ada GPUs have FP8 tensor cores but no FP4, so the target format is FP8. We built a pre-quantized export with a loader that never puts the bf16 weights on the GPU, so the 16 GB card does not have to hold the 18 GB original even briefly. For text-only serving, the two embedding tables, which Clef only reads row by row, stay in CPU memory, and the vision tower is not loaded.

FP8 with the bf16-output fallbacksamesame+0.02 pp [−0.23, +0.26]
  • The host-embedding build matched the FP8 export on all 1,264 transfer-v9 rows, with zero difference in any probability. It adds about 10 ms to short requests and under 2 % to long ones.
  • Ada's cuBLAS may not accept FP8 matmuls with fp32 output. The loader checks once at start and falls back to bf16 output if needed; both paths were measured above, and /v1/models reports which one is active.
  • FP8 brings no speed gain on this path. It is a memory saving.
  • Not yet run on an actual Ada card. Peak memory was measured with PyTorch's allocator capped at 15 GiB on the Spark; a real card also carries the CUDA context and any other process sharing it. spark/ada_validate.md has the steps and the expected answers to check against.

Method

How the numbers were made

  • Each experiment's read rule was written into the lab notebook before its data existed. Every scorer was first run on a positive control: identical reads scoring zero, and known-different reads scoring different.
  • Adversarial reviews ran at each milestone. They led to four recorded corrections: a double-applied temperature in the first scorer, an ECE criterion with no statistical power, "unknowable" rows wrongly counted in accuracy, and an overstated reading of the Clef card. A training-speed hypothesis was also retracted after uncontended measurements contradicted it.
  • All paired comparisons use a record-clustered bootstrap (2,000 resamples, seed 0).
